# NetArchitect: Recommendation & Config Engine

NetArchitect is an academic network planning application for the CIC-307 Computer Networks assignment. Its Python engine validates network inputs, allocates IPv4 subnets, recommends physical media and routing, explains the decisions, and generates Cisco IOS style configuration templates. A React, TypeScript, Vite, Tailwind, shadcn/ui, Lucide, and Recharts dashboard calls the REST API and renders the resulting topology and address plan.

> Generated configurations are design templates. Confirm platform syntax, interface mappings, addressing, provider policies, optical budgets, secrets, and change impact before applying them to equipment.

## Requirements

- Python 3.12 or newer
- Node.js 20.19+ or 22.12+ and npm
- Or Docker with Docker Compose

## Run locally

From this directory:

```bash
cp .env.example .env
cp frontend/.env.example frontend/.env
python3 -m venv backend/.venv
source backend/.venv/bin/activate
pip install -r backend/requirements.txt
cd backend
uvicorn app.main:app --reload
```

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:5173>. The API is at <http://localhost:8000>; interactive OpenAPI docs are at <http://localhost:8000/docs>. To point the UI at another API, edit `VITE_API_URL` in `frontend/.env`. The backend reads `NETARCHITECT_CORS_ORIGINS` from the root `.env`.

### Docker

```bash
docker compose up --build
```

The UI is served at <http://localhost:5173> and the API at <http://localhost:8000>.

## API

| Method and path | Purpose |
| --- | --- |
| `GET /api/health` | Service health |
| `GET /api/profiles` | Scenario catalog |
| `GET /api/profiles/{profile_id}` | One editable scenario |
| `POST /api/analyze` | Validate and analyze a complete design |
| `POST /api/validate` | Validate a design and overlap result |
| `POST /api/vlsm/allocate` | Allocate VLAN subnets |
| `POST /api/recommendations/media` | Recommend media for one link |
| `POST /api/recommendations/routing` | Recommend routing scope |
| `POST /api/configurations/generate` | Return separate IOS template files |
| `POST /api/configurations/export` | Download a ZIP of configuration files |
| `GET /api/audit-log` | Return the academic audit document |

Analysis requests contain `root_cidr`, a list of `{vlan_id, name, hosts}`, and optional `links` with `name`, `distance_m`, `requested_medium`, and `bandwidth_gbps`. The API returns structured HTTP 422 errors for invalid requests.

The Custom Network Builder edits network type, site/building/user/endpoint/device counts, VLAN host requirements, link distance/media/bandwidth, routing, latency, PoE, QoS, cloud, VPN, redundancy, and per source-VLAN destination ACL policies. Opposing overlapping ACL rules fail validation.

## Algorithm notes

- **Media:** deterministic planning classes use Cat6a through 100 m, OM4 through 400 m, and OS2 beyond 400 m. Copper explicitly requested beyond 100 m raises a distance violation. LR/ER selection is limited to 10 Gbps and a nominal 40 km ER class; higher rates are rejected for a rate-specific design, and longer paths return carrier-engineered transport without claiming a direct optic. The engine does not claim optical-budget feasibility. Confirm both vendor modules, fiber loss, connectors, splices, and received-power limits for each actual link.

  The 10GBASE-SR OM4, LR, and ER reach classes are cross-checked against the [Cisco 10GBASE SFP+ modules data sheet](https://www.cisco.com/c/en/us/products/collateral/interfaces-modules/transceiver-modules/data_sheet_c78-455693.html). The sheet also cautions that actual support is module-specific; the recommendation remains a planning class, not proof of vendor compatibility or link budget.
- **VLSM:** strict IPv4 root CIDR validation; requests are sorted by descending prefix size and allocated at aligned integer boundaries. A gateway address is reserved in addition to the requested endpoint host count. The allocator rejects duplicate VLAN IDs, invalid host counts, reserved subnet conflicts by placement, and exhaustion. `/31` and `/32` metadata are handled according to their special address semantics; general LAN demand allocation reserves network and broadcast addresses.
- **Routing:** single small domains use OSPF Area 0. Multiple sites/subnet scale use multi-area OSPF. Cloud or explicitly requested AS boundaries add eBGP. The decision depends on topology boundaries and scope, not user totals alone.
- **Metro latency:** a sub-5 ms value is treated as a target, not a guarantee. Carrier SLA and deployment measurements are required.
- **Visualization:** React Flow nodes and edges are constructed from the API topology response; the canvas supports pan, zoom, dragging, selection, and SVG export.

## IOS configuration files

Use the Configurations page to download the generated ZIP. The API returns a Layer 3 switch, access switch, and WAN router file for the current design. Sample profile exports live in `configs/`: each profile has a combined `*_config.txt`, a `*_configs.zip`, and individual device files under its profile folder. A complete Cisco Packet Tracer / GNS3 loading and verification log is available in `configs/VERIFICATION_REPORT.md`.

Several commands deliberately use conspicuous peer and secret placeholders because the project has no site handoff addressing, provider AS values, or secret source. The templates constrain trunk allowed VLAN lists, choose an unused high numbered native VLAN, default access ports to shutdown, generate ACLs from validated user rules, and add a clearly warned IoT policy when an IoT-named VLAN has no custom policy. The access switch template reserves the address after the management gateway for that template device; cloned switches need unique addresses and DHCP reservations. QoS, IKEv2/IPsec, and BGP excerpts require platform and policy completion before deployment. Multi-area OSPF areas and summaries require site-to-VLAN mapping, which the input model does not currently collect. The generator does not infer unspecified security policy or claim identical support across Cisco platforms.

## Viva topics

Be prepared to explain: Ethernet channel distance and PHY choice; multimode modal dispersion and single-mode optical budgets; VLSM prefix sizing, alignment, wildcard masks, broadcast and usable ranges; why IPv4 `/31` and `/32` differ from ordinary LAN subnets; VLANs, 802.1Q trunks, native VLANs and allowed VLAN restrictions; RSTP, PortFast and BPDU Guard; OSPF SPF, Area 0, multi-area boundaries and summarization; eBGP AS boundaries and route filtering; QoS classification and carrier SLA; IPsec/IKEv2 peer and key handling; ACL direction and packet matching; and the difference between a planning recommendation and a validated deployment.
